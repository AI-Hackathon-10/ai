# 임베딩 벡터 유사도 검색으로 알약 매칭 개선

## 한 줄 요약

> DB에서 글자가 정확히 안 맞아서 못 찾던 알약을, AI가 "의미가 비슷한 알약"을 찾아주는 보조 검색을 추가했다.

---

## 1. 왜 도입했는가

### 기존 방식의 문제

알약 사진을 찍으면 Vision AI가 각인·모양·색상을 읽어내고, 그 값으로 DB에서 `=`(정확 일치) 검색을 한다.

문제는 **DB에 저장된 색상값과 AI가 읽어낸 색상값이 글자 그대로 같지 않으면 못 찾는다**는 것이다.

**실패 예시: 탁센연질캡슐**

```
DB에 저장된 색상:   "청록, 투명"
AI가 읽어낸 색상:   "초록"

→ SQL: WHERE color_class1 = '초록'
→ DB에는 '청록, 투명'이라 저장되어 있으므로 → 매칭 실패!
```

사람이 보면 둘 다 같은 초록빛 캡슐인데, SQL은 글자가 다르면 무조건 실패한다. 이런 경우 사용자에게 **"식별 실패, 다시 촬영해주세요"**라고 안내하게 된다.

### 얼마나 흔한 문제인가

- DB에 등록된 알약 25,345건 중 `"청록, 투명"`, `"하양, 투명"` 같은 복합 색상값을 가진 항목이 상당수 존재
- 특히 연질캡슐(투명 겉껍질 + 내용물 색상)이 많이 해당
- 이 알약들은 사진을 아무리 잘 찍어도 SQL 매칭이 실패할 수밖에 없는 구조적 문제

---

## 2. 어떻게 해결했는가

### 핵심 아이디어

기존 SQL 검색은 건드리지 않고, **SQL이 못 찾았을 때만** "의미가 비슷한 알약 찾기"를 추가로 시도한다.

구체적으로:
1. DB의 알약 25,345건을 각각 한 줄짜리 텍스트로 변환한다
2. 이 텍스트들을 OpenAI 임베딩 모델로 숫자 벡터(1,536개의 숫자 배열)로 변환한다
3. 사용자가 찍은 사진에서 추출된 특성도 같은 방식으로 벡터로 변환한다
4. 두 벡터 사이의 유사도를 계산해서 가장 비슷한 알약을 찾는다

### 왜 이게 되는가

"청록, 투명"과 "초록"은 글자는 다르지만 의미는 비슷하다.
AI 임베딩 모델은 텍스트의 **의미**를 숫자로 바꾸기 때문에, 의미가 비슷한 텍스트끼리는 숫자도 비슷해진다.

```
DB 알약 텍스트:    "앞면각인: TAK-SEN | 모양: 타원형 | 색상: 청록, 투명 | 분할선: 없음"
사용자 쿼리 텍스트: "앞면각인: TAK-SEN | 모양: 타원형 | 색상: 초록 | 분할선: 없음"

→ 두 텍스트의 벡터 유사도: 0.9715 (97.15% 유사)
→ 충분히 높으므로 매칭 성공!
```

### 전체 흐름

```
사용자가 알약 사진 촬영
       ↓
Vision AI가 각인·모양·색상 추출
       ↓
① SQL 정확 매칭 시도 (기존과 동일)
       ↓
   찾았다 → 결과 반환 (여기서 끝)
   못 찾았다 → ② 벡터 유사도 검색 (새로 추가)
                    ↓
               유사도 높다 → 결과 반환
               유사도 낮다 → "식별 실패"
```

### 데이터 출처

별도의 벡터 DB를 쓰는 것이 아니다. 기존과 동일한 MySQL `pill_identification` 테이블의 데이터를 서버 시작 시 전부 읽어서 메모리에 벡터로 올려놓는 방식이다.

```
[서버 시작 시]
MySQL pill_identification 테이블 (25,345건)
       ↓ 전체 SELECT
각 알약을 텍스트로 변환
       ↓
OpenAI 임베딩 API로 벡터 변환
       ↓
메모리에 저장 (+ 디스크 캐시)

[요청 시]
Vision 추출 결과 → 텍스트 → 벡터 → 메모리에서 유사도 계산
```

## 3. 벡터 유사도 검색은 어떻게 동작하는가

### 핵심 — LLM을 다시 태우는 게 아니라, 미리 만들어둔 숫자 배열끼리 비교하는 것

벡터 검색은 크게 **두 단계**로 나뉜다. 준비 단계(서버 시작 시 1회)와 검색 단계(사용자 요청마다)다.

### 준비 단계: 서버가 켜질 때 1번만 실행

DB의 모든 알약을 미리 숫자 배열(벡터)로 바꿔놓는다. 이건 서버 시작 시 한 번만 하고, 이후에는 캐시 파일에서 불러온다.

```
┌─────────────────────────────────────────────────────────────────┐
│  서버 시작 시 (1회)                                              │
│                                                                  │
│  MySQL pill_identification 테이블                                │
│  ┌──────────────────────────────────────────┐                    │
│  │ 알약 1: TAK-SEN, 타원형, 청록/투명, ...  │                    │
│  │ 알약 2: TYLENOL, 장방형, 하양, ...        │                    │
│  │ 알약 3: TS LD, 장방형, 분홍, ...          │                    │
│  │ ...                                       │                    │
│  │ 알약 25345: ...                           │                    │
│  └──────────────┬───────────────────────────┘                    │
│                 ↓                                                │
│  각 알약을 텍스트 한 줄로 변환                                     │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ "앞면각인: TAK-SEN | 모양: 타원형 | 색상: 청록, 투명 | ..."  │    │
│  │ "앞면각인: TYLENOL | 모양: 장방형 | 색상: 하양 | ..."        │    │
│  │ ...                                                       │    │
│  └──────────────┬───────────────────────────────────────────┘    │
│                 ↓                                                │
│  OpenAI 임베딩 API (text-embedding-3-small)                      │
│  텍스트의 "의미"를 1,536개의 숫자 배열로 변환                       │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ 알약 1 → [0.023, -0.041, 0.087, ..., 0.012]  (숫자 1536개) │    │
│  │ 알약 2 → [0.015, -0.033, 0.052, ..., 0.008]  (숫자 1536개) │    │
│  │ ...                                                       │    │
│  └──────────────┬───────────────────────────────────────────┘    │
│                 ↓                                                │
│  메모리에 저장 + 디스크 캐시 (pill_vectors.pkl)                    │
│  → 다음 서버 시작 시에는 캐시에서 바로 로드 (OpenAI 호출 안 함)     │
└─────────────────────────────────────────────────────────────────┘
```

### 검색 단계: 사용자 요청마다 실행

SQL이 NO_MATCH일 때만 실행된다. **LLM(대화형 AI)을 다시 태우는 게 아니다.**
Vision 추출 결과를 같은 형식의 텍스트로 만들고, 임베딩 API로 숫자 배열 1개만 만든 뒤, 미리 저장해둔 25,345개 숫자 배열과 **수학적으로 비교**만 한다.

```
┌─────────────────────────────────────────────────────────────────┐
│  사용자 요청 시                                                   │
│                                                                  │
│  Vision AI 추출 결과                                             │
│  ┌────────────────────────────────────────┐                      │
│  │ 앞면각인: TAK-SEN, 모양: 타원형, 색상: 초록 │                      │
│  └──────────────┬─────────────────────────┘                      │
│                 ↓                                                │
│  ① SQL 정확 매칭 시도                                             │
│     WHERE print_front='TAK-SEN' AND color_class1='초록'          │
│     → 결과: 0건 (NO_MATCH)                                       │
│                 ↓                                                │
│  ② 벡터 폴백 시작                                                 │
│                                                                  │
│  쿼리 텍스트 생성                                                  │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │ "앞면각인: TAK-SEN | 모양: 타원형 | 색상: 초록 | 분할선: 없음"  │   │
│  └──────────────┬────────────────────────────────────────────┘   │
│                 ↓                                                │
│  OpenAI 임베딩 API 호출 (이것만 유일한 API 호출, LLM 아님)         │
│  텍스트 → 숫자 배열 1개                                           │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │ 쿼리 벡터 → [0.021, -0.039, 0.091, ..., 0.011]             │   │
│  └──────────────┬────────────────────────────────────────────┘   │
│                 ↓                                                │
│  numpy 내적 연산 (순수 수학 계산, API 호출 아님)                    │
│  쿼리 벡터 vs 미리 저장된 25,345개 벡터를 한번에 비교               │
│  ┌───────────────────────────────────────────────────────────┐   │
│  │ 쿼리 벡터  ·  알약1 벡터 = 0.9715  ← 97% 유사! (TAK-SEN)   │   │
│  │ 쿼리 벡터  ·  알약2 벡터 = 0.3120  ← 31% (TYLENOL)         │   │
│  │ 쿼리 벡터  ·  알약3 벡터 = 0.4500  ← 45% (TS LD)           │   │
│  │ ...                                                        │   │
│  │ → 유사도 0.75 이상인 것만 추려서 상위 5건 반환                │   │
│  └──────────────┬────────────────────────────────────────────┘   │
│                 ↓                                                │
│  결과: 탁센연질캡슐 (유사도 0.9715) → SINGLE_MATCH 확정            │
└─────────────────────────────────────────────────────────────────┘
```

### 정리: 뭐가 AI 호출이고 뭐가 아닌지

```
[준비 단계 — 서버 시작 시 1회]

  DB 데이터 읽기         → MySQL 조회          (AI 아님)
  텍스트를 숫자로 변환    → OpenAI 임베딩 API    (AI이지만 LLM 아님, 번역기 같은 것)
  숫자 배열 저장          → 메모리/캐시 저장     (AI 아님)


[검색 단계 — 요청마다]

  Vision 결과 → 텍스트    → 문자열 조합          (AI 아님)
  텍스트 → 숫자 1개 변환  → OpenAI 임베딩 API    (AI이지만 LLM 아님, 1회만 호출)
  숫자끼리 비교           → numpy 내적 계산      (AI 아님, 순수 수학)
  결과 정렬/필터          → 코드 로직            (AI 아님)
```

> **임베딩 API**는 ChatGPT 같은 LLM(대화형 AI)이 아니다.
> 텍스트를 숫자 배열로 바꿔주는 **변환기**에 가깝다. 대화를 생성하거나 추론을 하지 않는다.
> 비용도 LLM의 1/100 수준이고, 응답 시간도 수십 밀리초로 거의 즉각적이다.
>
> 벡터 검색의 핵심은 이 숫자 배열끼리의 **수학적 비교(내적)**이며,
> 이 비교 자체는 AI 호출 없이 서버 메모리 안에서 numpy로 즉시 계산된다.

## 4. 실제 테스트 결과

3개 알약으로 테스트했다.

### 타이레놀 (TYLENOL) — 기존 SQL로 바로 성공

```
AI가 읽은 것:  앞면=TYLENOL, 뒷면=500, 모양=장방형, 색상=하양
매칭 방식:     SQL 정확 매칭 (DIRECT_MATCH)
결과:          타이레놀정500밀리그람 — 즉시 확정
```

DB 색상값이 `하양`이고 AI도 `하양`으로 읽었으므로 SQL로 바로 찾았다.
벡터 검색은 실행되지 않았다 — **기존 동작에 영향 없음**.

### 탁센 (TAK-SEN) — SQL 실패 → 벡터로 복구

```
AI가 읽은 것:  앞면=TAK-SEN, 모양=타원형, 색상=초록
DB 저장값:     색상="청록, 투명"
SQL 매칭:      실패 ("초록" ≠ "청록, 투명")
벡터 매칭:     유사도 0.9715 → 탁센연질캡슐(나프록센) 확정
```

**개선 전**: "식별 실패, 다시 촬영해주세요"
**개선 후**: "탁센연질캡슐(나프록센)" 정확 식별, 효능·복용법까지 안내

### 탁센레이디 (TS LD) — 벡터로 후보 제시

```
AI가 읽은 것:  앞면=TS LD, 모양=장방형, 색상=분홍
벡터 매칭:     1위 탁센레이디연질캡슐 (0.9636)
               2위 세진정 (0.9275)
               → 1위와 2위 점수 차이가 작아 자동 확정하지 않음
결과:          후보 5건을 보여주고 사용자가 선택하도록 안내
```

**개선 전**: "식별 실패"로 끝
**개선 후**: 유력한 후보 목록 제시, 사용자가 직접 선택 가능

## 5. 비용과 성능

### 비용 — 거의 무료

| 항목 | 비용 |
|------|------|
| 최초 인덱스 빌드 (25,345건 임베딩) | **약 $0.03** (1회) |
| 이후 서버 재시작 | **$0** (캐시 파일에서 로드) |
| 사용자 요청 1건당 | **$0.000002** (사실상 무료) |

### 성능

| 항목 | 수치 |
|------|------|
| 서버 메모리 추가 사용 | ~150MB |
| 최초 기동 시 인덱스 빌드 | ~30초 (캐시 없을 때) |
| 이후 기동 | 즉시 (캐시에서 로드) |
| 요청당 벡터 검색 시간 | 1초 미만 |

### 안전장치

- 벡터 인덱스 빌드가 실패해도 서버는 정상 동작 (기존 SQL 매칭만 사용)
- SQL로 찾으면 벡터 검색은 실행하지 않음 (불필요한 API 호출 없음)
- 유사도가 낮으면 결과를 반환하지 않음 (잘못된 매칭 방지)

## 6. 기대 효과

### 직접 효과

- **매칭 성공률 향상**: DB 색상값이 복합값(`청록, 투명`)인 알약도 정확하게 식별 가능
- **사용자 재촬영 감소**: "식별 실패"가 줄고, 후보 목록이라도 제시하여 사용자가 직접 선택 가능
- **연질캡슐 대응**: 투명 껍질이 있는 캡슐류 알약의 식별 성공률이 크게 개선

### 간접 효과

- **표현 차이 대응**: AI가 `초록`이라고 읽든 `청록`이라고 읽든 의미적 유사도로 매칭하므로, 표현이 조금 달라도 찾을 수 있다
- **유지보수 편의**: 새로운 색상 조합이 DB에 추가되어도 별도 규칙을 만들 필요 없이 임베딩이 자동으로 대응
- **기존 동작 보장**: SQL 매칭이 성공하는 경우(타이레놀 등)는 기존과 완전히 동일하게 동작
